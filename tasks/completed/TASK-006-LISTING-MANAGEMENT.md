# TASK-006 — Listing Management Completion Report

## Summary

TASK-006 adds private landlord listing management on top of the existing
authentication, role, account-status, property ownership, property-image, and
Supabase foundations. An ACTIVE LANDLORD can create and manage rental listing
drafts for owned properties, submit a ready draft for review, pause or resume
an approved listing, and close a listing. Status, ownership, publication, and
closure timestamps are controlled by the backend.

No public discovery, application, messaging, viewing, or admin-approval feature
was added.

## API

All routes require a verified Supabase token, an application profile, ACTIVE
account status, and the LANDLORD role:

- `POST /api/v1/listings` creates a DRAFT for a server-verified owned,
  non-archived property.
- `GET /api/v1/landlord/listings` returns only the caller's listings with
  validated pagination and optional status filtering.
- `GET /api/v1/landlord/listings/:id` returns private owned detail, including
  private signed image URLs.
- `PATCH /api/v1/listings/:id` edits rental-cycle fields only while DRAFT or
  PAUSED.
- `POST /api/v1/listings/:id/publish` submits a ready DRAFT for review.
- `POST /api/v1/listings/:id/pause` pauses an ACTIVE listing.
- `POST /api/v1/listings/:id/activate` resumes a PAUSED listing after readiness
  is rechecked.
- `POST /api/v1/listings/:id/close` closes DRAFT, PENDING_REVIEW, ACTIVE, or
  PAUSED and is idempotent once CLOSED.

The route layer remains thin. Validation, state rules, publication readiness,
ownership, persistence, safe serialization, and provider-error translation are
separated into validators, middleware, services, repositories, and serializers.

## Listing State Machine

The centralized landlord state machine permits exactly:

```text
DRAFT          -> PENDING_REVIEW  (publish)
ACTIVE         -> PAUSED          (pause)
PAUSED         -> ACTIVE          (activate)
DRAFT          -> CLOSED          (close)
PENDING_REVIEW -> CLOSED          (close)
ACTIVE         -> CLOSED          (close)
PAUSED         -> CLOSED          (close)
CLOSED         -> CLOSED          (idempotent close)
```

`PENDING_REVIEW -> ACTIVE` is **not** available through any landlord API.
Publishing never creates an ACTIVE listing. RENTED and CLOSED cannot be edited,
and RENTED cannot be transitioned by a landlord. Invalid transitions return a
stable HTTP 409 error.

## Publication Readiness

Publish and paused-listing activation validate the persisted record rather than
trusting action-request fields. Readiness requires:

- valid title, description, positive monthly rent, deposit, available date,
  minimum lease, and maximum occupants;
- an owned, non-archived property;
- at least one persisted property image;
- exactly an available cover image for the property; and
- no other PENDING_REVIEW, ACTIVE, or PAUSED listing for that property.

The service returns stable readiness reasons for the frontend. The existing
partial unique database index remains the final concurrent-write protection;
its constraint error is translated to `LIVE_LISTING_ALREADY_EXISTS`. The
backend sets `published_at` only on DRAFT -> PENDING_REVIEW.

## Ownership

Property and listing ownership always comes from the verified auth user and
the caller's loaded landlord profile. Repository queries combine the resource
identifier with the authenticated landlord identifier. Client-supplied
`landlord_id`, ownership claims, or user IDs are never used as authority.
Cross-landlord reads and mutations use privacy-preserving not-found responses.

## Property Archive Integration

The TASK-004 archive flow now checks listings through the repository before
writing `archived_at`. A property with a PENDING_REVIEW, ACTIVE, or PAUSED
listing returns `PROPERTY_HAS_LIVE_LISTING` and remains unarchived. A property
whose listings are DRAFT only may still be archived. Publication also rechecks
archive state, so an archived draft cannot later be submitted.

## Mass Assignment

Strict request schemas reject protected or unknown fields. Tests cover attempts
to assign `id`, `property_id` during edits, `landlord_id`, `status`,
`published_at`, `closed_at`, `created_at`, and `updated_at`. Create status is the
database/backend DRAFT default, property identity is immutable after creation,
and transition timestamps are generated by the backend.

## Frontend

Landlord-only protected routes now provide:

- a paginated listing list with status filter, private cover thumbnails,
  loading/error/empty states, and status badges;
- listing creation with optional safe property preselection from owned property
  detail;
- DRAFT and PAUSED edit forms for rental-cycle fields;
- explicit “Submit for review” wording that explains the resulting
  PENDING_REVIEW state;
- readiness guidance for missing images and cover images plus backend readiness
  feedback;
- ACTIVE pause, PAUSED activate, and allowed-state close actions;
- read-only views for states that landlords cannot edit; and
- responsive, labelled, keyboard-accessible controls with visible feedback.

The frontend uses the centralized bearer-authenticated API client. It performs
no direct listing-table or Storage mutations.

## Security

- Authentication and ACTIVE LANDLORD authorization run before every listing
  operation.
- Ownership is enforced by authenticated, landlord-scoped backend queries.
- Listing status and transition timestamps are backend-controlled.
- Strict validation prevents protected-field mass assignment.
- RLS remains enabled and deny-by-default; no permissive policy was added.
- The browser performs no direct database writes or private Storage mutations.
- Private image paths remain hidden and landlord reads receive short-lived
  signed URLs only.
- No token, Supabase key, integration credential, or environment value is
  logged, copied into code, or committed.
